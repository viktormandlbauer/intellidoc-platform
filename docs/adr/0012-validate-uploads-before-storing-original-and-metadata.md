# Validate uploads in a temporary file and store the original before the metadata

## Context and Problem Statement

An upload must be checked for its size (REQ-DOC-1) and for being a valid PDF by its content (REQ-DOC-2), and its size and SHA-256 checksum must be stored with the metadata (REQ-DOC-3).
The original goes to the object store ([ADR-0011](0011-store-originals-in-rustfs.md)), while the document row and its outbox row go to PostgreSQL in one transaction ([ADR-0007](0007-deliver-processing-jobs-via-rabbitmq-with-transactional-outbox.md)).
The two stores share no transaction, so the order of the writes decides what is left behind when one of them fails.
A full content check needs the whole file, a declared `Content-Length` can be wrong, and a file of up to 50 MB must not be held in memory per request.
In what order is an upload received, validated and stored?

## Decision Drivers

* Size limit with 413 and content validation with 415, also for a wrong or missing `Content-Length` (REQ-DOC-1, REQ-DOC-2, AC-5.2, AC-5.3).
* The original is stored unchanged, with size and checksum (REQ-DOC-3, AC-6.2).
* No document row without its original, because a worker could not process it and a download would fail.
* No lost processing job ([ADR-0007](0007-deliver-processing-jobs-via-rabbitmq-with-transactional-outbox.md)).
* Bounded memory per upload in the API.
* Every error response generated by the API uses the JSON error format (NFR-8).
* Swagger UI is the demo client (`mvp.md` §3), so an upload must be possible from it.

## Considered Options

* Receive into a temporary file and validate it there, then store the original, then commit document and outbox row
* Stream directly into the object store, validate afterwards, then commit document and outbox row
* Commit the document row first (with an extra status such as `uploading`), then store the original
* Accept everything that starts like a PDF and let the worker reject invalid files

## Decision Outcome

Chosen option: "Receive into a temporary file and validate it there, then store the original, then commit document and outbox row", because it is the only option in which an invalid file reaches neither store and every document row has its original, without a new status.

Rules:

* **Request:** `multipart/form-data` with one file part, so Swagger UI offers a file picker.
  The body is read as a stream with a streaming multipart parser and never held in memory in full; the endpoint's OpenAPI schema is declared explicitly (NFR-8).
* **Size and checksum:** a declared `Content-Length` above the limit is rejected with 413 before reading.
  While reading, the API writes the file part to a temporary file, counts its bytes and updates its SHA-256; as soon as the count exceeds the limit, it stops reading and responds 413.
* **Validation:** the temporary file must start with the PDF header, open with a PDF library without a password and have at least one page; otherwise the API responds 415 (REQ-DOC-2).
  The library is a convention in [`CONTRIBUTING.md`](../../CONTRIBUTING.md); it must have a permissive licence (see [ADR-0008](0008-process-documents-with-docling-in-isolated-child-process.md) on PyMuPDF).
* **Order of writes:**
  1. generate the document ID;
  2. put the temporary file into the object store under a key derived from the document ID;
  3. in one transaction, insert the document row (`pending`, name, size, checksum, uploader, timestamp) and its outbox row;
  4. delete the temporary file, also on every error path.
* **Failure after step 2:** if the transaction fails, the API deletes the object as far as possible and responds with an error in the JSON format.
  An object that is left behind is not referenced by any document row and cannot be reached through the API; removing such objects belongs to the later purge of inactive data (`mvp.md` §5).
* **Name:** the client's file name is stored as metadata only, with path components removed and its length limited; it is never part of the storage key.
  A download sends it in the `Content-Disposition` header, encoded for non-ASCII characters.
* **Reverse proxy:** its body size limit is set slightly above the API's limit, so the API, not the proxy, answers an oversized upload with 413 in the JSON format.
* **Temporary files** live in a per-container scratch directory and are not state in the sense of assumption A-7; their disk space is sized for the size limit times the number of concurrent uploads.

### Consequences

* Good, because an invalid or oversized file reaches neither the object store nor the database.
* Good, because every document row has its original, so workers and downloads never meet a missing object.
* Good, because memory use per upload is bounded by the read buffer, independent of the file size.
* Good, because the outbox row is written in the same transaction as the document row, so no job is lost.
* Bad, because every upload is written twice (temporary file and object store); for files of at most the size limit this is acceptable.
* Bad, because a database failure after step 2 can leave an unreferenced object behind until a purge exists.
* Bad, because the API needs temporary disk space.
* Neutral, because streaming multipart parsing replaces the framework's convenience file parameter, so the upload endpoint needs a few more lines and an explicit OpenAPI schema.

### Confirmation

* AC-5.1 to AC-5.3 and AC-6.2 run as automated tests.
* Test: a chunked upload without `Content-Length` that exceeds the limit returns 413 in the JSON format and creates neither an object nor a document row.
* Test: a password-protected PDF returns 415.
* Test: if the database transaction fails after the object was stored, no document row exists and the response uses the JSON error format.
* Test: no temporary file remains after successful, rejected and failed uploads.

## Pros and Cons of the Options

### Temporary file, then object store, then metadata

* Good, because validation happens before anything is stored.
* Bad, because of the extra write and the temporary disk space.

### Stream directly into the object store, validate afterwards

* Good, because the file is written only once.
* Bad, because invalid files are first stored and then have to be deleted again.
* Bad, because validation has to read the object back from the store.

### Document row first, then the original

* Good, because no object can exist without a row.
* Bad, because it needs an additional status (`uploading`) beyond REQ-ING-2 and a cleanup of rows whose upload never finished.
* Bad, because the outbox row may only be written after the original exists, which needs a second transaction.

### Validation in the worker

* Good, because the API does the least work.
* Bad, because REQ-DOC-2 requires the API to reject invalid files with 415, which a later worker failure cannot provide.

## More Information

* Downloads stream the original from the object store after the access check; a repository or document without a role returns 404 before the first byte (REQ-ACL-3).
* Object storage is decided in [ADR-0011](0011-store-originals-in-rustfs.md), job delivery in [ADR-0007](0007-deliver-processing-jobs-via-rabbitmq-with-transactional-outbox.md).
